## ⚠️ 持久化语义（已定案，2026-10-08）
本引擎持久化语义 = **场景二（WAL-only 恢复，无快照层）**：
- `open()` 每次启动**全量重放** WAL 重建内存（无论上次干净/崩溃；区别只在是否做坏尾修复）。
- `close()` **保留日志**（这是存储引擎、重启不丢数据的保证）；收尾标记 = 完整性信号，
  恢复正确性命门 = **CRC + 坏尾处理(F9)**。
- 工业级「快照/表 + 短 WAL + MANIFEST」（场景一）为 P2 未来项，本轮不做（见 F11 历史改动）。

## 0. 一句话产品
一个**内存 KV 存储引擎**：数据按 key 有序存放，可增删查、可按 key 区间取到有序结果；
断电能靠日志恢复到崩溃前的完整状态；多线程访问安全。

## 1. 功能需求（必须全都有）

### 基础读写
- **F1** 写：`put(key, value)` 存一对 key-value；key 已存在时**覆盖** value（必须定义为覆盖）。
- **F2** 读：`get(key)` 取某个 key 的值；key 不存在时必须有明确的「不存在」信号（不能把空值当不存在，二者要能区分）。
- **F3** 删：`del(key)` 删除；删除一个不存在的 key 不应报错。
- **F4** 统计：能提供当前「条数」；空时能判断「是否为空」。

### 有序 + 范围（这是产品的核心卖点，不满足不收货）
- **F5** 数据必须按 key 的**大小有序**维护（不是哈希桶的顺序无关语义）。
- **F6** 区间查询：给定 `[最小, 最大]`（含两端）返回范围内全部 (key,value)，结果必须**有序**，并且是**这次调用独立的拷贝**。
- **F7** 必须能把有序结构的复杂度讲清楚：单 key 增删查目标平均 O(logN)，区间 O(logN+k)。

### 持久化 / 可靠性
- **F8** 崩溃恢复：进程中途挂掉，重启后能**恢复到崩溃前的完整写操作**（写得一半的按未写处理，见 F9）。
- **F9** 半条/损坏日志处理：日志尾部如果只有**写了一半的记录或校验不对**，恢复时只能保留前面完整的记录，坏的尾巴必须被**丢弃并截断**，不能当成有效数据。
- **F10** 落盘策略**三种可配置**：`每条都刷`（最稳最慢）、`每秒批刷`（折中）、`不主动刷`（最快，交给操作系统/调用方手动刷）。
- **F11** 干净关闭：本引擎为**存储引擎**（无快照/表层的场景二），`close()` 时**保留日志**、`open()` 时**每次全量重放**恢复；为此，干净关闭不删日志、不做坏尾修复（那是崩溃才需要的）。旧「缓存语义清理日志」作废。

### 并发
- **F12** 多线程安全：多个读可同时，写之间/读写之间互斥；你不能让用户拿到会悬垂的内部指针。
- **F13** 读操作返回的都是**值拷贝**，绝不能把引擎内部的地址/引用交出去。

## 2. 非功能需求（要写进你设计里的，不只是画饼）
- **N1** 语言标准：C++17。
- **N2** 分层约束（甲方架构要求，Redis 也这么做）：
  三者职责必须分开——① 只管有序数据结构本身（不粘磁盘、不粘锁）；
  ② 只管持久化日志；③ 门面/对外，把 ①、② 和并发组合成上面那套 F1-F13 对外接口。
  这三层**不允许揉在一个类里**。
- **N3** key/value 都是 `std::string`（二进制安全，别拿 strlen 数长度）。

## 4. 验收标准（最终 I 如何验证你合格）
你的接口搭好、再填上实现后，至少要能支撑以下四类场景：
1. **结构正确**：插入 N 个有序键 → 有序枚举全对；同 key 覆盖；删真移除；区间含边界。
2. **正确性金标准**：随机 10 万次 put/del/get，结果与标准有序容器（如 `std::map`）**逐一**比对，全部一致。
3. **崩溃恢复**：写一批不关机（模拟崩溃）→ 重启重放 → 与崩溃前一致；坏尾日志被正确截断。
4. **并发安全**：多线程混跑 get/put/del，在 ThreadSanitizer 下无数据竞争，结果与单线程重放一致。
