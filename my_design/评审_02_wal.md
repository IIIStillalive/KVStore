日期：2026-10-08

评审人：甲方（Claude）

## 结论
分区直觉比跳表初稿强很多（长度字段 + 校验和 + OP + 三态枚举，雷①预判到位），
但存在 **2 个「函数签名干不了活」** 的 P0、**1 个违反自身 N2 分层的架构硬伤**，
以及 2 个 P1 缺失。**当前版本甲方不予验收。**

## 🔴 P0 — 函数签名装不下它该干的活
1. `void log();` 无参数。追加一条日志需要 (op,key,val)，一个都没传——写不进任何东西。
   → append 必须带 (op, key, value)。
2. `bool CRC32();` 无参数。校验要针对具体数据，空参无法校验任何记录。

## 🔴 P0 — 架构硬伤（违反自身 N2 分层）
3. `bool recover();` 注释「调用跳表的插入接口」——把层②直接耦合进层①。
   WAL 职责是**只管持久化**：重放生成记录，交给门面应用；不该知道跳表存在。
   → recover 应返回 `vector<Record>`，由门面套进索引。依赖方向搞反了。

## 🟠 P1 — 缺关键件
4. 无 `open(path)`、无任何文件路径字段——Wal 无法连到一个日志文件。
   → 需要构造传路径 或 `open(path)`。
5. `is_clean_quit` 是进程内存标志，只能反映当次运行；`check()` 要回答的是**上一次**
   是否干净退出——必须靠磁盘标记 / 重放到 EOF+尾记录 CRC 合法来推断。纯内存 bool 不够。

## 🟡 雷②③ 未在接口回答（评审将追问）
- 雷② append：写盘 vs 改内存先后；崩在中间一致性以谁为准。
- 雷③ EverySec 的“每秒批刷”靠什么触发；No 模式的手动 flush 口子。

## ✅ 判断正确的部分（保留）
- `SyncMode` 枚举 + 构造参数注入（F10 三态可配）✓
- `LoggRecord` 长度字段 + 校验和（雷①）✓
- `OP{Put,Del}` 操作标记 ✓；`close()`（F11）✓
- 长度前缀而非 strlen（避开 N3 二进制坑）✓

## 验收判定
**不通过**。修 P0（参数补齐 + 拆掉 recover 对跳表的耦合）、补 P1（open + 干净退出落盘标记），
并答雷②③ 后可复审。

- **雷③接受**：EverySec 靠外部计时器调 flush()（合理取舍；无人调则退化为 No，需能讲出）

### 新 P0
1. **私有类型泄漏进公开签名**（编译错）：`SyncMode`、`LoggRecord` 在 private，却出现在公开 `Wal(SyncMode)` 构造 与 `recover()` 返回类型中 → 须把两者提到 `public:`（OP 可留私有）。
2. **`append(key,val)` 记不了删除**：无 op 维度，Del（无 val）与 Put 无法区分，重放无法应用删除 → 带 op 参数或拆 append_put/append_del。

### 旧账未还（P1）
3. `is_clean_quit` 仍为内存 bool，`check()` 无法回答「上一轮」是否干净退出 → 需 `close()` 落盘收尾标记，或重放到 EOF+尾 CRC 合法推断。

### 追问
- `CRC32(OP op)` 只收 op——校验若想揪「写一半坏尾」，CRC 须覆盖整条记录的长度+载荷字节，仅算 op 码拦不住。

### 「干净退出」答案 —— **EOF 哨兵模式，认可** ✓
- `close()` 在日志尾部落收尾标记；`check()` 读文件尾看标记是否存在 = 是否干净停，
  crash 无标记 = 需重放。比内存 bool 高明一档（来源落盘）。

### 待定（最后一片拼图）
- **clean-close 是否同时清 body（F11）**：
  - 方案A：截断清记录 + 留标记 → 盘态互斥（`[记录]+无标记`=崩需重放 / `[]+标记`=干净空），recover 不用跳标记。
  - 方案B：留记录 + 末尾加标记 → recover 需「见标记即停」，多一层处理。
  - 纯内存引擎按 F11 原意应取 A。**待用户定 A/B 并给原因。**

### 钉死的闭环
- 坏尾(F9)：读到长度越界或 CRC 不符 → 判定半条 → 停 + 截断。已靠 `CRC32(LoggRecord)` 罩整条兜底。

## 定案 02d（2026-10-08，持久化语义落案）

用户经真实业务考察（订单/聊天室）+ LevelDB 研究后，**层②持久化语义定案 = 场景二（WAL-only 恢复）**：
- **open() 每次启动都重放**（无论上次干净/崩溃），重建跳表；区别只在「是否做坏尾修复」。
- **close() 保留日志**（为保证「存储引擎、干净重启也恢复数据」，否决原 F11 缓存语义——需求规格据此改版）。
- 收尾标记 = 完整性信号（非正确性命门）；**恢复正确性命门 = CRC + 坏尾处理(F9)**。
- 工业标准（LevelDB/RocksDB = 场景一 + 编号WAL + MANIFEST + 快照，正常关闭弃旧WAL、下次开新WAL）本轮只作认知储备；本引擎因无 SST 层、checkpoint 划 P2，先按场景二落地，WAL 增长/全量重放记入 P2 欠账。
- **正确性层次**：marker≠跳过重放（除非有快照）；CRC+坏尾=正确性命根；跳过重放=仅场景一成立。
